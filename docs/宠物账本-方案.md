## 0. 一句话定位

**一个「冰箱贴 + 账本」二合一的家用宠物物资管家**：首页是宠物画廊，第二屏是补给看板（谁快没了、谁快过期、放在哪），账本退到第三屏——但报表页用「日均成本」把记账和库存焊死在一起。

**差异化只有一个**：市面上记账 App 管钱、库存 App 管货，只有把两者接起来才能算出「这袋粮每天花我多少钱」。这是唯一别人抄不走、也最难做假的功能。

## 2. 信息架构

底部 4 Tab + 1 悬浮主按钮：

```
┌─────────────────────────────────────────┐
│  ① 画廊    ② 补给看板   ③ 洞察   ④ 我的   │
│              【＋ 记一笔】悬浮圆钮         │
└─────────────────────────────────────────┘
```

### 2.1 首页 · 宠物画廊（Gallery）

```
        🐱 豆豆         🐶 团子        ＋
     ├ 专属告警 1 条    ├ 无告警       加宠物
     └ 本月 382 元?     └ —
```

- 卡片 = 头像（照片或 SVG）+ 名字 + 品种年龄 + **专属商品告警徽标**
- 卡片**不显示金额**（Q28：共享池下这是伪指标）
- 底部一行家庭级提示：「家里 2 件东西快过期 →」
- 点卡片 → 宠物详情：基本资料、专属商品、该宠物名下的账单（明确标注「仅统计专属商品」）
- 无宠物时：空状态引导「先登记第一只毛孩子」+ 品种 SVG 选择器

### 2.2 补给看板（Pantry）—— 实际最常用的一屏

三段式：

```
⚠️ 快过期（7 天内）      🍚 该补货（<5 天量）
─────────────────────────────────────────
[猫粮 1.5kg] 剩 12 天     [豆腐砂] 剩 3 天
冰箱侧门 · 2026-12-03     阳台储物柜
─────────────────────────────────────────
📦 全部库存（按位置 / 品类筛选）
```

- 每个商品卡：名称、余量、日耗、剩余天数、位置、最早到期日
- 天数为负 → 「已断粮 N 天」红标
- 卡片右下角：`出库 -1` 一键扣减（伴随微动效，Android 上额外有震动）
- 顶部搜索 + 按位置/品类筛选

### 2.3 记一笔（Quick Add）—— 模态，非独立页

1. 默认 1 行：商品（可搜索/新建）→ 数量 → 单价 → 到期日 → 位置
2. 「＋ 再加一件」插入行
3. 底部实时合计
4. 保存 → 撒星星 + 连续记账天数 +1（Android 上附加震动）

**关键设计**：新建商品时就地填「日均消耗」，一步到位，避免二次编辑。

### 2.4 洞察（Insights）

- 顶部：本月总支出（大数字滚动）、环比箭头（数据不足则显示解锁提示）
- 品类占比：环形图（粮/砂/医疗/玩具/其他）
- 月度趋势：折线 + 柱状切换
- **日均成本榜**：Top 5「最贵的一天」商品 —— 这是核心差异化
- 顶部宠物切换器：全部 / 单只（单只时角标注明「仅统计专属商品」）

### 2.5 我的（Me）

- 宠物管理（新增/编辑/换头像）
- 品类与提醒阈值
- 位置管理
- **数据：导出 JSON / 导出 CSV / 从备份恢复 / 自动备份开关**（P0）
- 关于、版本、开源许可

## 3. 数据模型

### 3.1 ER 概览

```
pet ──┐
      │ (nullable)
category ─ product ──┬── purchase_item ── purchase
                     ├── stock_batch
                     └── stock_movement
location ────────────┘
```

### 3.2 表定义

```sql
-- 宠物
CREATE TABLE pet (
  id            TEXT PRIMARY KEY,
  name          TEXT NOT NULL,
  species       TEXT NOT NULL CHECK (species IN ('cat','dog','other')),
  breed         TEXT,
  birthday      TEXT,           -- ISO date
  gender        TEXT CHECK (gender IN ('male','female','unknown')),
  avatar_type   TEXT NOT NULL DEFAULT 'svg',  -- 'svg' | 'photo'
  avatar_ref    TEXT,           -- svg key 或 本地图片相对路径
  note          TEXT,
  sort_order    INTEGER NOT NULL DEFAULT 0,
  created_at    TEXT NOT NULL
);

-- 品类（内置 5 类，可增删）
CREATE TABLE category (
  id                  TEXT PRIMARY KEY,
  name                TEXT NOT NULL,
  icon                TEXT,
  color               TEXT,          -- HEX
  remind_days         INTEGER NOT NULL DEFAULT 7,   -- 临期阈值(Q21)
  low_stock_days      INTEGER NOT NULL DEFAULT 5,   -- 补货阈值
  sort_order          INTEGER NOT NULL DEFAULT 0
);

-- 商品（SKU 级）
CREATE TABLE product (
  id                TEXT PRIMARY KEY,
  name              TEXT NOT NULL,
  category_id       TEXT NOT NULL REFERENCES category(id),
  unit              TEXT NOT NULL DEFAULT '件',      -- 袋/罐/盒/支
  spec              TEXT,                            -- "1.5kg" 等展示用
  daily_usage       REAL NOT NULL DEFAULT 0,         -- 日均消耗(件/天)，0=不预测
  remind_days       INTEGER,                         -- 覆盖品类阈值
  track_batch       INTEGER NOT NULL DEFAULT 0,      -- 0=商品级 1=批次级(Q27)
  note              TEXT,
  archived          INTEGER NOT NULL DEFAULT 0,
  created_at        TEXT NOT NULL
);

-- 位置（单级）
CREATE TABLE location (
  id          TEXT PRIMARY KEY,
  name        TEXT NOT NULL UNIQUE,
  icon        TEXT,
  sort_order  INTEGER NOT NULL DEFAULT 0
);

-- 采购单
CREATE TABLE purchase (
  id          TEXT PRIMARY KEY,
  occurred_at TEXT NOT NULL,          -- ISO datetime
  total       REAL NOT NULL DEFAULT 0,
  note        TEXT,
  created_at  TEXT NOT NULL
);

-- 采购明细行
CREATE TABLE purchase_item (
  id            TEXT PRIMARY KEY,
  purchase_id   TEXT NOT NULL REFERENCES purchase(id) ON DELETE CASCADE,
  product_id    TEXT NOT NULL REFERENCES product(id),
  qty           REAL NOT NULL,        -- 数量（件）
  unit_price    REAL NOT NULL,        -- 单价（元/件）
  subtotal      REAL NOT NULL,        -- qty * unit_price
  expiry_date   TEXT,                 -- 该行到期日
  location_id   TEXT REFERENCES location(id),
  pet_id        TEXT REFERENCES pet(id)  -- NULL = 共享池
);

-- 库存批次（存储层始终用批次；UI 默认按商品汇总）
CREATE TABLE stock_batch (
  id               TEXT PRIMARY KEY,
  product_id       TEXT NOT NULL REFERENCES product(id),
  purchase_item_id TEXT REFERENCES purchase_item(id) ON DELETE SET NULL,
  qty_in           REAL NOT NULL,
  qty_left         REAL NOT NULL,
  expiry_date      TEXT,
  location_id      TEXT REFERENCES location(id),
  received_at      TEXT NOT NULL,
  opened_at        TEXT
);

-- 出入库流水（唯一真相来源，用于审计与重建）
CREATE TABLE stock_movement (
  id          TEXT PRIMARY KEY,
  product_id  TEXT NOT NULL REFERENCES product(id),
  batch_id    TEXT REFERENCES stock_batch(id),
  type        TEXT NOT NULL CHECK (type IN ('in','out','adjust')),
  qty         REAL NOT NULL,          -- out 为负
  happened_at TEXT NOT NULL,
  note        TEXT
);

-- 应用元信息（连续天数、等级、设置）
CREATE TABLE app_meta (
  key   TEXT PRIMARY KEY,
  value TEXT
);

-- V2：预算
-- CREATE TABLE budget (id TEXT PRIMARY KEY, month TEXT, amount REAL);
```

### 3.3 关键派生量

```sql
-- 商品当前库存
SELECT product_id, SUM(qty_left) FROM stock_batch
WHERE qty_left > 0 GROUP BY product_id;

-- 剩余天数
remaining_days = total_qty / NULLIF(daily_usage, 0)

-- 日均成本（差异化核心）
daily_cost = unit_price * daily_usage
-- 依据：unit_price 元/件，daily_usage 件/天

-- 最早到期日
SELECT MIN(expiry_date) FROM stock_batch WHERE product_id=? AND qty_left>0
```

### 3.4 关于「商品级 vs 批次级」的存储策略（重要）

用户选了**商品级**（Q27）。但一个到期日字段在数学上无法表达「3 袋不同批次」。

**方案：存储永远用批次，UI 默认按商品聚合。**

| 层 | 行为 |
|---|---|
| 存储 | 每次入库生成一条 `stock_batch`（数量 + 到期日 + 位置） |
| 默认 UI | 一个商品 = 一个「当前数量」+ 一个「最早到期日」，用户完全看不到批次 |
| 拆批次 | 商品设置里打开 `track_batch=1`，列表行展开为多批次，出库需选批次 |
| 出库 | 默认**先进先出（FEFO：先到期先出）**全自动，用户零感知 |

这样既满足了「商品级录入体验」，又不会在「买 3 袋」那天给出错误的到期日。**录入成本零增加，正确性零损失。**

## 4. 核心流程

### 4.1 记一笔（Φ 目标：≤ 15 秒）

```
点【＋】→ 商品搜索(首次则新建：名称/品类/单位/日均消耗)
       → 数量 → 单价 → 到期日(默认按品类预设保质期自动填) 
       → 位置(默认上次位置) → 保存
       → 撒星星 + 连续天数 +1 + 库存批次写入（Android 附加震动）
```

### 4.2 出库

```
补给看板卡片 → 点「-1」→ 先进先出扣减 → "-1" 飘字（Android 附加震动）
           （长按 → 自定义数量，V1.5）
```

### 4.3 过期提醒

- 触发：`expiry_date - today <= category.remind_days`
- 展示：补给看板顶部「⚠️ 快过期」段 + 首页家庭级提示条 + Tab 红点
- **不做系统级通知**（V1：浏览器通知需授权且各端差异大）；V1.5 再评估 Notification API + PWA

## 5. 视觉设计系统

### 5.1 方向：**奶油软糖 + 纸感手账**

- 底色暖奶油而非纯白（纯白冷硬、显廉价、夜间刺眼）
- 卡片大圆角 + 柔和双层阴影，像贴纸浮在纸上
- 插画统一**手绘线条风 SVG**：2px 圆头描边 + 单色填充 + 一个高光点
- 账本区叠极淡纸纹（SVG noise，透明度 3–5%）
- **强调色全应用只留一个**，且只出现在当下唯一的主操作上

|---|---|---|

### 5.3 插画清单（手绘 SVG，共约 30 个）

| 类别 | 数量 | 说明 |
|---|---|---|
| 品种头像 | 8–12 | 猫（橘/白/狸花/奶牛/布偶）、狗（柯基/柴/金毛/泰迪）、其他（兔/仓鼠） |
| 品类图标 | 5 | 粮袋、砂盆、药瓶、球、礼盒 |
| 状态表情 | 5 | 开心、饿、困、生病、庆祝（用于宠物卡与空状态） |
| 空状态 | 4 | 无宠物、无库存、无账单、无数据 |
| 装饰 | 3–4 | 纸纹、星星、爪印、分隔花边 |

> 部分可借「豆包/即梦生图」生成参考图，但**最终交付必须手写成 SVG**——位图在 Web 包里体积大、风格难统一、且无法做描边动画。
>
> 生图 API 的一手能力（火山方舟 `images/generations`）：`background: transparent` 可直出带 Alpha 的 PNG；`layer_decomposition` 能把一张图拆成最多 99 个透明图层（含 `z_index`/`bounding_box`/`name`），适合拿来做分层动效素材。**但没有 `seed` 参数，风格一致性锁不死**——靠多张参考图 + 固定提示词模板 + 人工筛选，不要设计「种子复现」流程。

## 6. 技术架构

### 6.1 选型

| 层 | 选择 | 理由 |
|---|---|---|
| 壳 | **纯 Web SPA**（静态托管 / PWA） | 无安装、跨设备打开即用；代价见 §8、§10 |
| 前端 | React 19 + TypeScript + Vite | 生态成熟，动效库支持最好 |
| 样式 | Tailwind CSS v4 + CSS 变量 tokens | 快速迭代，tokens 直接映射 |
| 动画 | **Motion**（原 framer-motion） | 原生 spring 原语，`useSpring`/`layout` 动画，最贴近多邻国手感 |
| 图标/插画 | 手写 SVG 组件 | 可改色、可描边动画、零请求 |
| 数据库 | **sql.js（WASM SQLite）**，内存库 + 二进制持久化到 IndexedDB | 保留完整 SQL 与 §3 表结构；`db.export()` 出来的就是 `.sqlite` 文件，直接当备份 |
| 状态 | Zustand + TanStack Query | 轻量，避免 Redux 的仪式感 |
| 图表 | 手写 SVG | 数据量小（<1000 点），引库反而增加体积与风格割裂 |
| 备份 | 导出 JSON/CSV + 本地定时快照 | 「不丢数据」P0 |

### 6.2 为什么没有传统「后端」

需求原文写了「需要简单的前端和后端」，但在**单机 / 离线 / 不登录 / 不共享**四个约束下，后端的每一项职责都不成立：

| 后端职责 | 本项目是否需要 |
|---|---|
| 数据持久化 | sql.js 在浏览器内存里跑，定期 `export()` 落 IndexedDB；SQLite 不需要服务端 |
| 鉴权 | 无账号 |
| 多端同步 | 明确不做 |
| 业务逻辑隔离 | 本地单用户，无攻击面 |
| 定时任务 | 应用启动时结算即可 |

**结论：纯 Web 形态下没有「后端」这个角色，只有一个静态站点 + 浏览器内数据库。**

> ⚠️ 纯 Web 的代价必须写清楚：**浏览器存储不是「你的磁盘」，它可以被清掉**（用户清缓存、Safari 7 天未访问回收、隐身模式关闭）。因此「不丢数据」这个排第一的约束，在 Web 形态下**只能靠「定期导出 + 显式提醒用户下载备份」来兑现**，不能靠「数据在本地所以安全」。这是形态切换付出的真实代价，不是实现细节。

## 7. 动效规范（多邻国式）

### 7.1 曲线与时序

```css
--ease-spring: cubic-bezier(0.35, 1.8, 0.35, 0.83);  /* 过冲回弹：抄的多邻国线上实测值 */
--ease-out:    cubic-bezier(0.22, 1, 0.36, 1);       /* 减速（多邻国也在用这条） */
--dur-micro:   140ms;    /* 按压/切换态 */
--dur-card:    240ms;    /* 卡片进出 */
--dur-page:    300ms;    /* 页面转场（多邻国主节奏就是 .3s，线上 CSS 里出现 53 次） */
--dur-celebrate: 800ms;  /* 庆祝 */
```

**核心原则：多邻国的「流畅」70% 来自过冲曲线 + 240–350ms 的短时长 + 错峰 stagger，不是复杂资产。**

> 证据（来自反查 duolingo.com 生产环境 CSS）：`animation-duration: .3s` 出现 53 次；仅有的两条贝塞尔中有 `cubic-bezier(.35,1.8,.35,.83)`，第二控制点 y=1.8 > 1 即「弹过头再回位」。这是**实测值，不是官方设计规范**——多邻国未公开 motion token。

**工具选择**：用 **Motion**（原 framer-motion）而非 Rive。理由：Rive 运行时 canvas-lite 压缩后 222KB 且需 WASM 双文件、必须用 Rive Editor 制作、免费版导出带启动水印（商用需 $9/seat/月）；而 Motion 仅 63KB(gzip) 纯 JS，`bounce: 0.2~0.35` 就是过冲，零设计师、零授权费。**Duolingo 用 Rive 是因为它有专职「creative technologist」岗位**，这个成本我们不背。

> 唯一可能引 Rive 的条件：需要「根据用户输入实时切换表情」的角色状态机。V1 不做——我们的宠物头像只要眨眼/摇尾，用 SVG 分组 + CSS 即可。

### 7.2 动效清单

| # | 场景 | 动效 | 时长 |
|---|---|---|---|
| 1 | 按钮按压 | `scale 1 → 0.96`，底边阴影 3px → 1px | 140ms spring |
| 2 | 卡片入场 | `translateY 12px + opacity 0→1`，列表 **stagger 50ms**，最多 6 项 | 240ms |
| 3 | 金额数字 | countUp 滚动（tabular-nums 防抖动） | 600ms ease-out |
| 4 | 出库成功 | 「-1」飘字上浮淡出 + 卡片轻微下沉 | 240ms |
| 5 | 入库/记账成功 | 卡片弹跳 + **撒星星**（12 个粒子抛物线） | 800ms |
| 6 | 页面切换 | 淡入 + 上浮 8px（不做左右位移，桌面端会晕） | 300ms |
| 7 | 连续打卡火焰 | 呼吸缩放 `1 → 1.06` 循环 | 2s loop |
| 8 | 等级进度条 | 宽度 spring 填充 + 数值同步滚动 | 600ms |
| 9 | 临期告警 | 进入视口时摇摆 `rotate ±3°` 一次 | 400ms |
| 10 | 宠物头像 | 悬停/点击时眨眼（SVG 分组位移）、偶尔摇尾 | 200ms |
| 11 | 空状态 | 插画上下浮动 loop | 3s |

### 7.3 反向风险（必须写进验收）

> **动效过量会让记账变成表演。**

- 任何动效**不得延迟用户操作**（动画期间控件必须已可交互）
- 尊重 `prefers-reduced-motion`：开启时全部降级为 fade，撒星星改为静态
- 连续使用 30 天后仍觉得「烦」的动效 = 需要删除的动效
- 撒星星只在**记账成功**触发，**出库不撒**（高频动作，撒一次就够了，撒三次成噪音）

## 8. 震动反馈（纯 Web 形态下的裁决）

### 8.1 事实核查

| 通道 | Android | iOS | 桌面浏览器 |
|---|---|---|---|
| Web `navigator.vibrate()` | ✅ Chrome / Firefox / 三星浏览器 | ❌ **Safari 全版本不支持**（caniuse 实测数据，含最新版） | ❌ 无硬件 |

**结论：改为纯 Web 后，iPhone 上「永远拿不到震动」。** 这不是实现难度问题，是 Safari 从未实现 Vibration API。要震动就必须有原生壳，而这与「只做 Web」的决策直接冲突。

### 8.2 裁决

- **能做**：Android Chrome 下 `navigator.vibrate()` 可用。做一个 `haptic(kind)` 适配层，能力存在就调，不存在就静默返回 `false`——业务零感知、零阻塞。
- **不做**：不为了震动引入 Tauri / Capacitor / 原生壳。**震动是加分项，不是需求项**，不值得为它推翻交付形态。
- **iOS 的补偿**：用动效 + 音效承担反馈。iOS Safari 下可用 `pointerdown` 触发的轻量视觉脉冲替代震感，成本几乎为零。

### 8.3 震动语义映射（仅 Android 生效）

| 交互 | 类型 | 说明 |
|---|---|---|
| 选择品类 / 切换 tab | `tap` | 最轻 10ms |
| 出库成功 | `tap` | 高频动作，不加重 |
| 记账成功 | `success` | 与撒星星同步，一次 |
| 临期 / 断货告警出现 | `warning` | 仅在用户主动进入看板时 |
| 升级 / 连续天数里程碑 | `celebrate` | 稀有才值钱 |

### 8.4 反向风险

> **震动是「在 Android 上很爽、在 iPhone 上完全不存在」的不对称体验。** 如果为了它去纠结「为什么我手机上没反应」，说明它不该成为设计的核心反馈通道——所有关键状态都必须有**视觉**表达，震动只是锦上添花。

| 风险 | 影响 | 缓解 |
|---|---|---|
| **浏览器存储被清空**（Web 形态下的头号风险） | 致命——直接击穿「不丢数据」这条首位约束 | ① 每次写入后 debounce 持久化；② 应用启动时若检测到「上次使用距今 > 7 天」强制弹备份提醒；③ 导入/导出双向可用；④ V1.5 转 PWA 以规避 Safari 的 7 天回收 |
